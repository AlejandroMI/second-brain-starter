# Practices to Adapt to the User

These are optional approaches for any agent using this vault. Choose what serves the current request, available access, and the user's preferences. They do not install routines, require integrations, or authorize external actions. A quick capture can stay a quick capture.

## Use Current Context

For a review or planning request, useful evidence may include Home, relevant projects and areas, recent journal entries, and the live systems the user has connected. Consult only what helps the task. If Calendar or GitHub is unavailable, work from the accessible notes and state the limit rather than imply a live check.

Home is orientation. Project and area notes hold durable current context; journal plans and weekly recaps describe a point in time. Software repositories, relevant branches and working changes, issues, and PRs own implementation state. Calendar owns scheduled times, while the original source owns a deadline. A fresh user correction may show that an external entry needs updating; retain the correction and its date rather than blindly trusting a stale label.

A weekly review can ask what changed, what finished, what remains unresolved, and what matters next. After a long pause, a useful alternative is a catch-up: reconcile old plans with current evidence before carrying them forward. Do not interpret silence or an old `active` label as proof of current priority, or automatically turn possibilities into commitments.

## Follow Through on Outcomes

Match the level of follow-up to what the user is doing. When status matters, distinguish intention, preparation, scheduling, submission, and confirmation in ordinary prose; a new tracking database is unnecessary.

For example, preparing a fictional reading-club invitation does not mean it was sent. A venue visit in Calendar does not prove attendance. A submitted booking request may still await confirmation. Record what the user reports or what the system actually verifies, with its source, and leave unknown outcomes open.

Calendar can help put an agreed action into time and avoid conflicts when access is available. Check live availability before proposing precise slots. Creating or moving events needs authorization for that action; a habit is not permission to create a recurring event. When an important commitment is unresolved, a focused follow-up may be more useful than another general reminder.

## Keep Journaling Active and Useful

When the user wants reflection, recent notes can support a specific question: "Last time the venue was the blocker; did that change?" Prefer grounded curiosity over repeating a generic questionnaire. The user can answer in text or, if the runtime supports it, through a voice capture workflow.

Respond to the purpose of the moment. Sometimes listening and preserving the experience is useful; sometimes the user wants analysis or next actions. Do not turn every entry into advice, an evaluation, or a compulsory closing question. Separate the user's words from the agent's interpretation. Keep dated notes at `01_Journal/YYYY-MM-DD.md`; weekly recaps or special sections can live within that day's note.

## Let Corrections Improve Continuity

Use corrections to repair relevant context instead of adding a second conflicting version. A dated episode can stay in the journal; a durable preference about the user's needs may belong in the relevant area; a choice with rationale may deserve a decision note. Preserve provenance and avoid deriving a permanent personality profile from one exchange.

The agent manages its own technical lessons, tone, and execution rules in its runtime. Do not copy those into the vault or change runtime settings as a side effect of capture. This distinction allows different agents to use the same durable context without inheriting another agent's personality.

## Offer Proactivity as an Option

If the user wants scheduled support, possible approaches include a morning orientation, a reflection prompt, or a weekly review. Choose timing and frequency with the user rather than installing all three. A useful routine can stay quiet when nothing warrants attention, while checking unresolved important commitments before choosing silence.

Configured, executed, delivered, and useful are different claims. Verify the actual experience before describing an automation as working. Account for quiet hours, timezone, available context, and machine connectivity. Keep schedules and delivery state in the runtime. When several agents are in use, agree which owns a reminder so they do not send duplicates; see [Sharing a Vault](Sharing%20a%20Vault.md).
